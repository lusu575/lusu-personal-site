# 工具雷达视觉方法论

这份文件是每周“工具雷达”的固定选图、制图与验收方法，不是某一期试稿的临时修图说明。核心原则只有一句：**先写清这张图要帮读者看懂什么，再去找图；找不到合格画面就不放。**

图片是正文证据和解释的一部分，不是用来填空、调节版面或证明“这个网站存在”的装饰。契约允许因版权或质量原因省略图片，但编辑目标是每个工具一张、必要时最多两张；文字核验充分却确实没有合格图片时，工具仍可入选。

## 一、先写视觉任务卡

在打开官网、截图或制图前，先为每个计划使用的画面写一张视觉任务卡。任务卡至少包含：

- **读者问题**：读者看这张图前最想知道什么，例如“我把一句自然语言交给它以后，真正会得到什么？”
- **视觉结论**：看完图后读者应该能够复述的一句话，例如“它会把文字指令落到可继续编辑的视频时间线，而不是只生成一段建议。”
- **必须出现**：能够证明上述结论的关键元素，通常包括工具身份或功能标题、输入或触发动作、主要处理状态，以及输出或成果。只列真正必要的 2–5 项。
- **画面关系**：标记为“单图自洽”“步骤一／步骤二”或“之前／之后”。需要两张图时，先写清二者各自负责什么。
- **三语图注规划**：先用一句话确定图注要引导读者看哪里，再分别写中文、英文、日文图注。
- **风险检查**：计划使用的来源、权利依据、是否需要登录、是否含个人数据、画面是否可能频繁失效。

没有视觉任务卡，不开始截图。任务卡写不出明确“读者问题”和“视觉结论”，通常说明这张图没有必要存在。

写入运行记录时，每张已选图片使用同一套可审计字段；下面是单图骨架，完整约束仍以 `run.schema.json` 为准：

```json
{
  "assetPath": "assets/images/articles/tool-radar/<edition-date>/<file>.png",
  "sourceUrl": "https://...",
  "rightsBasis": "official-permitted-download",
  "sha256": "<64 位小写 SHA-256>",
  "alt": { "zh": "...", "en": "...", "ja": "..." },
  "caption": { "zh": "...", "en": "...", "ja": "..." },
  "captureBrief": {
    "readerQuestion": "...",
    "visualClaim": "...",
    "informationRole": "result",
    "mustShow": ["产品或功能身份", "关键动作", "完整结果"]
  },
  "framing": "standalone",
  "sequence": null,
  "visualQa": {
    "threeSecondTestPassed": true,
    "productAndContextIdentifiable": true,
    "criticalContentUncropped": true,
    "privacyClean": true,
    "articleWidthReadable": true,
    "reviewedAt": "<本期执行窗口内的 ISO 时间>"
  }
}
```

这些布尔值不是占位默认值，只能在逐张实际查看后登记为 `true`。任何一项尚未确认，就不要把图片写进运行记录。

## 二、单图与双图的叙事契约

### 单图必须自洽

单张图连同图注，必须在离开正文段落后仍能回答：

1. 这是哪个工具或哪项功能；
2. 用户做了什么，或画面处于哪个明确步骤；
3. 画面展示了什么结果、能力或限制；
4. 这与正文里的哪一句结论有关。

纯首页、Logo 墙、空编辑器、没有结果的输入框、只剩浏览器边框的长截图都不算自洽。若一张界面图只能说明“入口在哪里”，却不能说明“它能带来什么”，应补成有明确步骤关系的双图，或改用原创说明图。

### 双图必须形成一段完整关系

同一工具使用两张图时，二者必须拥有明确顺序和互补信息，只接受以下关系：

- **输入／输出**：第一张交代输入、提示词或素材，第二张交代可观察的结果；
- **操作／结果**：第一张说明关键动作，第二张说明动作完成后的界面或产物；
- **之前／之后**：两张保持可比较的对象、范围和比例，清楚展示变化；
- **步骤一／步骤二**：两个连续且必要的步骤，缺少任一张都会让流程不完整。

图注必须写明“先看什么、再看什么”，不能把两张互不相关的官网页面并排，也不能用同一页面的两个随意裁切冒充流程。

## 三、画面如何截才算完整

截图要围绕视觉任务裁切，而不是围绕浏览器视口裁切。

- 工具名称、功能标题或可识别的产品上下文至少保留一种；若为避免冗余不保留 Logo，图注必须明确工具与功能。
- 用来证明结论的关键标题、输入、触发动作、输出和结果不得被导航栏遮挡，不得只露一半，也不得在左右或底部被切断。
- 裁切范围既要去掉无关区域，也要给标题、控件、卡片和结果留下合理留白。不要紧贴文字边缘，不要保留大片空白或无关浏览器外壳。
- 长页面只截取一个语义完整的区块。不能从任意滚动位置截一屏，让读者既看不到区块标题，也看不到结果结尾。
- 界面缩放后必须保证正文宽度下仍可读；不能依靠读者打开原图才能辨认关键文字。
- 三语共用同一图片时，图内视觉必须语言中立，或同时让中、英、日读者理解；不得让英文或日文正文依赖中文长句才能完成三秒测试。
- `articleWidthReadable=true` 必须来自实际窄屏检查：至少在 359、375、390px 三种文章视口宽度中验证关键身份、动作和结果仍可辨，不能只检查 1200px 原图是否溢出。
- 固定导航、Cookie 条、聊天气泡、账号菜单和动画中间帧会破坏语义时，应等待稳定状态、关闭遮挡或重新取景。
- 画面不能包含账号、邮箱、头像、访问令牌、密钥、订单、付款信息、私有项目名、未公开素材或其他个人数据。

## 四、三秒测试

每张候选图在进入文章前都要脱离正文做一次“三秒测试”。只展示图片与图注，三秒后让审阅者回答：

- 这是什么工具或功能？
- 用户做了什么？
- 结果或价值在哪里？
- 图注让我重点看哪里？

四项中任一项无法回答，就不能把这张图视为完成。对于双图，还要额外确认读者能看出先后关系，并能说出第二张相对第一张新增了什么信息。

三秒测试不是要求把所有文字塞进图片，而是要求截图、顺序和图注共同形成一个有头有尾的视觉句子。

## 五、图注、alt 与正文的分工

- 每张公开图片必须有中文、英文、日文图注和 alt。
- **alt 描述画面里客观可见的内容**，方便无法看到图片的读者理解画面。
- **图注说明这张图在本节证明什么，并引导读者看关键位置**；不要只写“官网截图”“操作界面”或复述工具名。
- 三语图注必须表达同一个视觉结论和同一组先后关系，可以自然本地化，但不能分别增加不同事实。
- 正文负责解释背景和判断，图片负责提供具体视觉证据，图注负责连接二者。不要让图片承担正文没有核实的额外宣传结论。

## 六、来源与权利优先级

公开文章按以下顺序选择素材，前一档无法满足视觉任务时才进入下一档：

1. **本站原创、可复现的演示**：使用安全的自制输入或公开示例，记录操作条件，分别保存输入、步骤和输出；不得运行来路不明脚本或上传私有文件。
2. **明确允许转载或下载的官方素材**：例如官方媒体包、许可条款明确的产品截图或经书面授权的素材；保存来源页面、许可说明和核对日期。
3. **本站原创说明图**：根据已经核实的产品事实，重新绘制流程、输入／输出或使用场景图；不得复制受保护界面，也不得把概念图伪装成真实产品截图。
4. **无图**：没有明确权利、无法稳定复现或无法讲清楚含义时，直接省略图片。

在官网公开可访问，不等于拥有转载权。为首期试稿截取的官网页面只用于本地人工审稿和讨论取景方法，不代表官网授予转载授权，也不得直接成为正式文章资产。正式发布仍须回到以上优先级重新获得可用素材和权利依据。

所有公开图片必须复制到 `assets/images/articles/tool-radar/<edition-date>/`，禁止远程热链，并记录规范来源、权利依据、核对日期和 SHA-256。来源页面不稳定、素材会话过期、依赖登录或无法在未来复核时，不进入公开稿。

## 七、每周固定执行顺序

每期按以下顺序工作，不能先随手截一批图再为它们补理由：

1. 完成候选发现、永久去重和官方事实核验。
2. 确定本期一句话叙事主线、工具顺序和每节要说的核心结论。
3. 默认给每个入选工具规划一张能独立说明核心结论的图；只有版权、隐私、稳定性或窄屏可读性门禁无法通过时才保持无图，确有连续关系时才增加第二张。
4. 为每个计划画面写视觉任务卡，先决定单图或双图关系。
5. 按来源与权利优先级获取素材，完成裁切或原创制图。
6. 写三语 alt 与图注，保存来源、权利、核对日期、文件哈希和本地资产路径。
7. 逐张执行语义完整性、三秒测试、裁切可读性、版权、隐私和稳定性检查。
8. 只有通过的图片才进入三语正文；三语必须使用同一组图片、同一顺序和同一视觉结论。
9. 在运行记录校验通过后才允许进入部署；有图的正式期必须先把本期资产随 `main` 经 GitHub → Cloudflare Pages 正常路径部署，生产投递器再从线上读取每张图片并核对精确 SHA-256。只有线上图片与审阅字节完全一致时才允许创建文章。

## 八、失败关闭

图片是可选项，但一旦写进运行记录或正文，就必须通过全部视觉闸门。任何一项不合格时，只能选择：

1. 按同一视觉任务重新截图或重新裁切；
2. 改成基于已核实事实的本站原创说明图；
3. 从三语文章和运行记录中一起删除该图片。

不得用泛化 Hero、空截图、失焦画面、低清图、随意裁切或来源不明素材占位；不得只修中文而让英文、日文继续引用旧图。含不合格图片的运行记录必须停止校验和投递，直到图片被修复或移除。图片被移除不会自动淘汰已经通过文字事实核验的工具。
